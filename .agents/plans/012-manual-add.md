# 012 — `/checklist add` (manual task entry)

Status: done — npm test 88/88 green, tsc clean, tracked dist rebuilt; source print-mode + tmux TUI smoke verified

## Goal

Let the human add a task by hand: `/checklist add` opens a TUI dialog with an
autogenerated, editable 3-char id, a task-text field and a multiselect picker
over the existing tasks for `dependsOn`. Submitting runs basic state validation
only — dependencies do **not** have to be done and nothing checks blocking or
readiness, so a `planned` task that depends on unfinished work is fine.

## Research (pi docs read in full: `tui.md`, `extensions.md`; examples `questionnaire.ts`, `tools.ts`, `qna.ts`)

- `ctx.ui.custom(factory, { overlay: true, overlayOptions })` for the dialog, same
  as the existing checklist/settings dialogs; finish only through `done()`.
- Components must keep every line within `width` (`visibleWidth`/`truncateToWidth`),
  invalidate on state change, and a component that shows a cursor must be
  `Focusable` and forward `focused` to the `Input` it wraps (IME placement).
- Use `Input` for text fields, `matchesKey`/`Key` for keys. `Input` always draws a
  reverse-video fake cursor, so only the focused text field renders through it.
- pi-tui slices an overlay to `maxHeight` without scrolling → the dialog windows the
  picker itself (same trick as `ChecklistOverlay`, `dialogMaxRows`).
- Print/RPC have no custom components → guard with `ctx.mode === "tui" && ctx.hasUI`.

## Design

1. **Store (`src/store.ts`, pure)**
   - `suggestTaskId(current, rng?)` — random free 3-char id (not used by any task *or
     subtask*, not reserved).
   - `validateAddTask(current, draft)` → field errors: `id` (3 × `[a-z0-9]`, not `all`,
     unique across tasks+subtasks), `title` (non-empty), `dependsOn` (each must be an
     existing task; no self), `form` (capacity `MAX_CHECKLIST_TASKS`). Deliberately
     **no** done/blocked/ready checks.
   - `addTask(current, draft)` → `{ ok, checklist, task } | { ok: false, errors }`,
     validating then appending through `createOrAppend` (single source of truth for
     building tasks, cycles etc.).
   - Fix: `createOrAppend` append mode did not count *existing subtask ids* as used, so
     a new task could reuse one; seed `used` with them (task-only `taskIdSet` kept).
2. **Dialog (`src/add-task-dialog.ts`)** — `AddTaskDialog` component (Focusable) drawn
   with `frameDialog`. Fields: ID (`Input`, sanitized to ≤3 `[a-z0-9]`), Task (`Input`),
   Depends on (checkbox picker, windowed). Validation errors render inline under the
   fields and focus jumps to the first bad field; the dialog stays open.
3. **Command (`src/commands.ts`)** — `/checklist add [title…]` (+ `add` in completions,
   usage string). TUI: opens dialog (title prefilled from the args). Capacity is
   checked up front. Non-TUI: with a title adds directly with an auto id, without one
   asks for TUI mode.
4. **Wiring (`src/index.ts`)** — `addTask` dep: validates against the *live* checklist
   (agent may have changed it while the dialog was open), then `commit()` →
   state + `pi.appendEntry` + `refreshUi` (widget/footer).
5. **Tests** — `tests/manual-add.test.mjs`: store validation matrix, id suggestion,
   subtask-id collision, no-blocking-validation, dialog keyboard flow/windowing/
   narrow widths/focus, command wiring + persistence.
6. **Docs** — README (command, keys, validation rules), AGENTS.md (status + facts).
7. **Verify** — `npm test` (rebuilds tracked `dist/`), `tsc --noEmit`, `pi -e ./src/index.ts`
   print mode, tmux TUI smoke.

## Keyboard UX

- Opens with focus on **Task** (id is already filled in).
- `Tab` / `Shift+Tab` or `↑` / `↓` move between ID → Task → Depends on.
- Picker: `↑`/`↓` (or `j`/`k`) move, `Space` (or `x`) toggles, `↑` on the first row
  returns to Task.
- `Enter` adds the task from any field. `Ctrl+R` rolls a new random id.
  `Esc` / `Ctrl+C` cancels.
